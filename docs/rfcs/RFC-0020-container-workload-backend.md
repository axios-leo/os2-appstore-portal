## 1 职责口径（一句话）

**集群方给承载能力，OS² 做承载决策**（0820 会议原话方向：「手脚你们实现，我们做大脑」）。
OS² 只经标准 K8S REST 调用集群方容器平台；不接管集群、不改集群、不在集群方组件里驻留代码。

## 2 决策

### 2.1 后端族切换点，process 为缺省

沿用 `make_dds_adapter`/can-sim 的工厂先例：`orchestrator.backend` 二值。
`process`＝RFC-0017 的 EM 进程面，**缺省，存量行为逐字节不变**（回切自证入判据）；
`k8s`＝新适配器，把「拉起服务实例」翻译为标准 K8S 对象（Deployment/Pod + resources 请求），
「回收」翻译为删除；存活与水位从 K8S watch + 既有 ResourceReport 双源对账。

### 2.2 只用标准面，三关键项前置

只调标准 K8S REST，OS 决策与平台实际执行的边界不变。DEMO3 使用的具体平台与物理身份按 [设计基线 §2](../DEMO3_DESIGN.md#2-三项集成与完整范围) 接收；不再用“随 709/716 现装”替代东大实机核验，也不将实际 K8S API 集成统称为仿真桩。

平台接收表须包含 CRD、调度扩展位、资源调整方式（含原地调整可用性）、工作节点、网络、存储与权限。功能取决于实际版本、开关和配置，不能只凭名称或版本号判已可用；不支持分支须明确拒绝或经批准的替代执行方式，不静默换成成功。716 已有的版本反馈是接口对账输入，不是东大安装证据。

### 2.3 管理面不托管

core-01 / hmi-01 / hmi-02 及注册中心**不迁 K8S**——OS² 自身的控制面不能依赖被它调度的平台
（裁判不住运动员家）。K8S 只承载业务负载：通算节点容器、链B 动态实例、夸父 Pod 组。

### 2.4 生命周期证据闭环

拉起/回收事件走 RFC-0017 既有主题（载荷 +`runtime=process|k8s-pod`）；
占用账本、TTL 回收、within_budget 裁决沿用 M2.3 机制，容器实例与进程实例同一账本口径。
镜像来源＝应用商店验签后制品；**制品与镜像是两级摘要，见 §2.5**。

### 2.5 制品入集群的路径与摘要对象（2026-08-31 补，负责人当日定职责切分）

**职责切分**：**工厂在岸侧——构建、打包、加签**；**应用商店在端侧 core 域——分发**。岸侧不设中心仓，
全系统一个商店实例。商店跑在管理面（不迁 K8S，§2.3），镜像要跨到被管集群，路径定为：

`.os2pkg` **内含 OCI 归档** → 商店验签入库准入 → 激活时把归档 `import` 进目标节点的 containerd
→ k8s 后端按本地镜像起 Pod。**不自建镜像仓**（与首表「不做」一致）。

**摘要是两级，不是一个。** `os2-pack` 产出的 `<id>-<ver>.tar.gz` 的 sha256 是**包摘要**；
containerd 与 K8S 认的是**OCI image-manifest 摘要**（归档 `index.json` 里那个）。**两者不是同一个对象**，
`ArtifactPublish` 清单须**同时记两级**，展演台按两级显示，**不得用一个数字冒充三点**。
因此「三点一线」的精确表述是：

- **包摘要**：工厂产出 ＝ 商店在架；
- **镜像摘要**：包内 image-manifest ＝ 节点 containerd 已导入 ＝ Pod 实际运行镜像。

**前车之鉴**：Q-018／Q-019 两次被测试侧拒收同源——`.Id` 随镜像存储后端漂移、取错了摘要对象，
而本侧六道门全绿（`IMPLEMENTATION_LEDGER` §4-8/§4-9：**判据必须作用在会出问题的那个对象上**）。
核对复用 `mk_release.py::normalize_archive_platform`（扁平 descriptor 补 platform，只加字段不改 blob、
digest 不漂）与 `verify_release.py` 的离线核对。

### 2.6 更新策略执行与承载编排的接线（2026-08-31 补）

`ActivationCommand` 的激活**必须落到集群的实际动作**，而不是只改商店记录。此前商店侧
`on_activated` 扩展点与 `workload-orchestrator` 之间**没有线**——本 RFC 补这条线，
事件与账本沿用 §2.4 同一主题、同一口径。

接线要承载的是**每节点每服务的更新策略三档**（§2.7 的 `mode`），各档落到不同的实际动作：

| 档 | `mode` | 集群侧动作 | 现场可见的证据 |
|---|---|---|---|
| **预置** | `PRELOADED` | 命中节点本地既有镜像，**不向商店取件**，直接起 Pod | 取件计数不涨；Pod 运行镜像＝基线镜像摘要 |
| **更新最新** | `UPDATE_AND_CACHE` | 与商店比版本，有新版才取件并**换镜像重起 Pod**，无新版走本地 | 有新版时取件一次 + Pod 镜像摘要变化 |
| **每次重下** | `ALWAYS_DOWNLOAD` | 每次激活都取件后起 Pod | 每次激活取件计数 +1 |

**回滚是本机制的特例**（＝激活上一版本），走同一条线，不另设通道。
**发布决策仍在商店（CSCI-08），编排只执行**，边界不变。

### 2.7 更新策略三档的模型变更（2026-08-31 补，模型 schema，消息面零改动）

`contracts/models/manifest.schema.json` 两处改动：

1. **`mode` 枚举补 `PRELOADED`。** 现有 `DOWNLOAD_AND_CACHE` 的语义是"首次下载后缓存"，
   与"**节点基线自带、运行期零下载**"不是一回事；把后者按前者填，预置档的证据（取件计数不涨）
   第一次就不成立。补成四值：`PRELOADED` / `UPDATE_AND_CACHE` / `ALWAYS_DOWNLOAD` /
   `DOWNLOAD_AND_CACHE`（后者保留，存量真件零变化）。
2. **`mode` 下沉到 `artifacts[]` 制品级。** 现在一份清单一个值＝**节点级**，表达不了
   "同一节点上 A 服务预置、B 服务每次重下"，而策略本来就是**按节点按服务**设的。
   改为 `artifacts[]` 每项可带 `mode`，清单级 `mode` 降为**缺省值**（不写即继承），
   存量真件（只有清单级 `mode`）行为逐字节不变。

**写入方与执行方分开**：部署计划由 **CSCI-09 岸侧工厂**生成，`mode` 在那时按服务写定；
**CSCI-08 端侧商店**按 `mode` 执行分发与激活。两册须同口径，改一处必改另一处。
